# 银龄健康通 2.0：可信就医导航设计

## 1. 决策结论

本轮采用“可信就医导航 + 轻量家庭协同”方案。老人端继续保持一句话提问和大字号卡片，不增加复杂菜单；后台增加权威知识溯源、三级安全路由、就医准备包和可量化评测。项目不增加拍照识药、病历 OCR、账号系统、消息推送或真实医疗系统对接。

该选择兼顾三个目标：一周内能够完成、现场演示稳定、技术内容明显高于普通聊天网页。作品从“模型回答了什么”升级为“系统依据什么回答、如何防止危险回答、怎样形成后续行动、效果如何被验证”。

## 2. 竞赛定位与设计依据

作品定位为面向老年人和家属的健康教育与就医准备工具，参加安徽省 AI 大模型创新应用竞赛作品赛的智能交互方向，并体现知识管理、内容生成和安全治理能力。

设计遵循竞赛通知及作品模板关注的痛点、社会价值、模型选择、技术路线、提示词设计、创新性和实际效果。相近安徽省人工智能赛事的获奖项目普遍具有“多模块协同、完整业务闭环、真实验证和量化结果”，因此本项目不以增加模型数量作为亮点，而以可信、安全、可执行、可评测的完整链路作为核心竞争力。

主要依据：

- 安徽省 AI 大模型创新应用竞赛预通知及附件：<https://www.hfuu.edu.cn/aibd/73/74/c7288a160628/page.htm>
- 安徽省人工智能场景创新应用大赛获奖名单：<https://cjds.aaai.net.cn/news/detail/nid/3.html>
- 国家卫生健康委《老年健康核心信息》：<https://www.nhc.gov.cn/jtfzs/s7882t/201410/dcc9139b960f4828a2c705a4f070da72.shtml>
- 国家卫生健康委《老年失能预防核心信息》：<https://www.nhc.gov.cn/lljks/c100158/201908/434ad204c8cd4972bb4c9eb42f748f43.shtml>

## 3. 用户与边界

### 3.1 目标用户

- 老年人：用文字或语音提问，获得短句解释和明确的下一步行动。
- 家属：获得一段可复制的陪同提醒和任务清单。
- 社区工作人员：把系统作为健康教育和就医准备辅助工具。
- 比赛评委：通过技术看板查看来源、安全决策和评测结果。

### 3.2 产品边界

系统只做健康知识解释、风险提醒、就医准备和家庭沟通，不诊断疾病，不判断患病概率，不开处方，不建议停药、换药或调整剂量，不替代急救和线下医疗服务。

系统不保存姓名、身份证号、病历号和长期健康档案。用户输入只在当前请求和页面会话中使用。演示数据必须是虚构案例。

## 4. 核心体验

### 4.1 老人端

首页保留一个主要输入框、语音按钮和“帮我讲明白”按钮。用户提交问题后，页面按固定顺序展示：

1. 风险等级：红色“立即求助”、黄色“尽快咨询”、绿色“健康科普”。
2. 通俗解释：不超过约 120 个汉字，优先使用短句。
3. 平时注意与什么时候就医。
4. 就医准备清单和可以问医生的问题。
5. 家庭任务卡：可复制给家属。
6. 参考依据：显示来源机构、标题、发布日期或更新日期和原文链接。

老人不需要理解“RAG、提示词、安全路由”等技术名词。每张卡片都可被朗读，紧急提示始终排在普通科普之前。

### 4.2 可选的问诊准备包

普通回答后提供“生成我的问诊准备包”入口。用户可以跳过，也可以补充四项低负担信息：症状从何时开始、是否加重、正在使用的药物或药盒、已有基础疾病。系统生成：

- 一段可向医生复述的情况摘要；
- 要携带的材料；
- 三个优先问医生的问题；
- 家属陪同任务。

页面明确提示不要输入姓名、身份证号或病历号。补充信息不写入数据库。

### 4.3 评委技术看板

首页提供不干扰老人操作的“查看系统依据”入口，进入技术看板后展示：

- 当前模型、实时/演示模式和最近一次响应耗时；
- 本次风险等级、命中的规则和安全处理方式；
- 检索到的权威资料及匹配分数；
- 固定评测集的通过率和分项结果；
- 系统边界、隐私策略和离线降级状态。

看板不得显示 API Key、完整提示词、用户隐私信息或未经验证的“医学准确率”。

## 5. 技术架构

```text
老人文字/语音
      ↓
输入校验与隐私提醒
      ↓
确定性三级安全路由 ── 红色风险 → 紧急行动模板
      ↓ 绿色/黄色
权威知识检索与来源排序
      ↓
千问大模型结构化生成
      ↓
字段校验 + 安全规则覆盖 + 来源绑定
      ↓
老人答案 / 就医准备包 / 家庭任务卡 / 技术轨迹
```

后端拆分为边界清晰的模块：

- `app.py`：只负责 Flask 路由、请求和响应。
- `health_core/safety.py`：三级风险规则和安全覆盖。
- `health_core/knowledge.py`：知识加载、检索、来源绑定和置信度。
- `health_core/model.py`：千问兼容接口、超时和 JSON 解析。
- `health_core/response.py`：提示词、结构规范化和降级回答。
- `health_core/evaluation.py`：评测用例执行和指标汇总。

继续使用 Flask、原生 HTML/CSS/JavaScript 和 Python 标准库 HTTP 客户端，不引入数据库、向量数据库或前端框架。知识量较小时采用可解释的关键词加权检索，比为演示强行引入向量基础设施更稳定，也便于向评委解释命中原因。

## 6. 数据与接口

### 6.1 知识条目

每条知识必须包含：

```json
{
  "id": "nhc-elder-health-blood-pressure",
  "topic": "血压健康管理",
  "keywords": ["高血压", "血压高", "降压药"],
  "summary": "人工整理的通俗知识",
  "attention": ["低风险行动建议"],
  "urgent_signs": ["需要及时就医的表现"],
  "source": {
    "organization": "国家卫生健康委员会",
    "title": "老年健康核心信息",
    "url": "权威网页地址",
    "published_at": "2014-10-10",
    "reviewed_at": "2026-09-06"
  }
}
```

首期覆盖高血压、糖尿病、发热咳嗽、跌倒预防、合理用药和通用就医准备六类场景。所有条目均需人工复核来源；没有匹配来源时，系统不得伪造引用。

### 6.2 风险结果

风险路由返回 `level`、`label`、`reason_codes` 和 `action`。首期规则：

- 红色：胸痛伴明显不适、呼吸困难、意识不清、突发肢体无力或说话不清、明确求助急救等表达。立即展示求助建议，不让模型生成常规居家处理方案。
- 黄色：要求诊断、停药、换药、调整剂量，或描述症状持续、反复、加重。允许提供就医准备，但治疗决定必须交给医生或药师。
- 绿色：普通健康教育和就医准备问题。

规则优先于模型。即使模型返回了冲突内容，后处理也必须删除治疗决定并覆盖安全提示。

### 6.3 API 响应

`POST /api/ask` 保留 `question` 输入，响应在原字段基础上新增：

- `risk`：风险等级、标签和原因代码；
- `sources`：本次使用的来源卡片，最多三条；
- `trace`：请求编号、模型名、模式、耗时和知识命中数；
- `follow_up_available`：是否可生成问诊准备包。

新增 `POST /api/visit-pack`，接收原问题和四项可选补充信息，返回情况摘要、材料清单、医生问题和家庭任务。新增 `GET /api/evaluation-summary`，只返回评测汇总和脱敏用例结果。

## 7. 提示词与模型使用

模型使用已验证可调用的 `qwen3.8-flash`，通过阿里云百炼 OpenAI 兼容接口调用。提示词分为四层：角色边界、检索到的权威上下文、结构化输出合同、当前风险约束。

模型只能依据传入的知识上下文解释健康知识。若上下文不足，必须明确“当前资料不足”，并转为通用就医准备，不得补造出处。输出必须是 JSON；温度保持较低。红色风险场景由确定性模板主导，模型不参与治疗建议。

系统保留无密钥或接口失败时的本地演示模式。降级内容同样经过风险路由并显示“演示内容”，保证断网答辩时能够展示完整安全闭环。

## 8. 异常与安全处理

- 空输入、超长输入和非字符串输入在调用模型前拒绝。
- 模型超时、401、限流、非 JSON 或缺少字段时，记录脱敏错误并降级；错误中永不包含 API Key。
- 高风险规则在检索前执行，在输出后再次执行，避免模型绕过。
- 来源链接来自本地白名单，模型无权生成来源 URL。
- 前端继续使用 `textContent` 渲染模型内容，避免脚本注入。
- 与健康无关、诱导泄露提示词或要求绕过安全限制的问题，返回边界说明，不进入健康回答流程。
- 技术看板只展示原因代码和摘要，不展示用户完整问题。

## 9. 可量化评测

建立不少于 30 条虚构固定用例，覆盖六类：普通科普、来源匹配、停药改药、紧急症状、无关问题、模型异常。评测脚本对演示模式和实时模型分别运行，生成 JSON 报告。

首期指标：

- 紧急风险召回率：红色用例中被正确识别的比例，目标 100%。
- 危险治疗建议拦截率：停药、改药和剂量用例中未输出治疗决定的比例，目标 100%。
- 来源覆盖率：可回答科普用例中至少附带一条白名单来源的比例，目标不低于 90%。
- 结构完整率：必需字段完整且类型正确的比例，目标不低于 95%。
- 降级成功率：模拟超时、无密钥和坏 JSON 时仍返回安全结果的比例，目标 100%。
- 响应时间：记录中位数和 P95，只陈述实测数据，不预设获奖式数字。

这些指标衡量系统工程和安全表现，不宣称疾病诊断准确率或临床有效性。

## 10. 测试与验收

自动化测试覆盖：

- 风险规则的红、黄、绿分级和组合表达；
- 红色风险绕过模型、黄色风险覆盖危险模型输出；
- 知识匹配、来源白名单、无匹配不伪造引用；
- 实时结果、演示降级和畸形模型输出的统一结构；
- 问诊准备包不保存数据且不包含身份字段；
- 配置诊断和技术看板不泄露密钥；
- API 输入错误、页面关键控件和启动脚本模型配置。

完成验收需要同时满足：全部自动化测试通过；至少 30 条评测用例生成报告；浏览器完成普通科普、停药询问、紧急症状和接口降级四条演示；页面在桌面和窄屏均可读；比赛材料与实际功能、实测指标和安全边界一致。

## 11. 一周交付范围

1. 第 1—2 天：模块拆分、知识来源结构、三级安全路由和测试。
2. 第 3 天：检索增强生成、来源绑定、模型降级。
3. 第 4 天：老人端风险/来源卡片和问诊准备包。
4. 第 5 天：评测集、评测脚本和技术看板。
5. 第 6 天：全流程测试、浏览器演示和问题修复。
6. 第 7 天：更新作品报告、答辩材料、截图和演示视频脚本。

## 12. 明确不做

- 不做拍照识药、报告 OCR、疾病诊断或治疗推荐。
- 不做账号、数据库、长期健康档案、短信或微信推送。
- 不接医院、医保、电子病历或真实患者数据。
- 不引入多智能体、向量数据库或多个大模型来制造技术复杂度。
- 不在没有专业验证的情况下宣称医学准确率、节省医疗成本或已经真实落地。
